## Найденные проблемы и исправления

### 1. Критический риск: актуальные секреты внутри отслеживаемого архива

`.claude/tmp/src.tgz`, добавленный в Git, содержал корневой `.env` и `HotelSiteBackend/.env`. Пароли БД и ключи внутри архива совпали с текущими локальными настройками. Значения не выводились в чат, отчёт и результаты тестов. Архив был добавлен коммитом `7444a3e` от 27.10.2026. Более ранняя история также содержала backend `.env` с прежними секретами.

При совпадении ключа с production обладатель копии репозитория мог подписывать административные JWT. Наличие секретов в Git подтверждено; общедоступность репозитория, чужой доступ и совпадение с боевыми секретами не установлены.

**Сделано:** архив удалён из рабочего дерева и индекса; временные архивы, логи, `.env` исключены из новых коммитов и Docker build context. Локальный `JWT_SECRET` заменён новым случайным значением и синхронизирован с локальным backend `.env`, права файлов — `0600`. Сгенерированный backend `node_modules` исключён из индекса, вместо него используется lock-файл.

**Осталось обязательно:** заменить боевой JWT-ключ, пароль БД и остальные опубликованные секреты; очистить историю и старые артефакты. Пароль существующего PostgreSQL автоматически не менялся: изменение одной `.env` без изменения роли в БД отключило бы приложение. История Git не переписывалась и force push не выполнялся.

### 2. Высокий риск: неавторизованный запрос мог завершить процесс API

`controllers/userController.js`: Express 4 получал обычный `async`-обработчик без передачи отклонённого Promise в `next()`. Для существующего email значение `password: {}` вызывало отказ bcrypt, после которого отдельный процесс завершался с кодом 1. Ошибки БД в других необёрнутых async-контроллерах создавали похожую возможность.

**Исправлено:** строгая Joi-валидация типов/размеров, JSON-only вход, `express-async-handler` для всех прежде необёрнутых контроллеров, корректные 400/409/413 вместо необработанного отклонения. Тест доказывает, что некорректный вход больше не останавливает процесс.

### 3. Высокий риск: сессия не отзывалась и могла продлеваться бессрочно

`utils/session.js`, `controllers/userController.js`: полномочия брались только из JWT. Смена пароля, удаление пользователя и понижение роли не проверялись; logout удалял cookie только в браузере. `/auth` выпускал новый семидневный JWT из старых claims. Подписанный JWT с несуществующим администратором принимался и продлевался; украденный JWT продолжал работать после logout.

**Исправлено:** серверные `admin_sessions`, случайный `jti`, проверка существующего пользователя и актуальной роли в БД на каждом запросе, связь с текущим хешем пароля. Выход удаляет серверную сессию. Смена пароля, роли или удаление пользователя лишают старую сессию полномочий. Абсолютный предел — 12 часов, неактивность — 30 минут; `/auth` не увеличивает абсолютный срок. Проверка JWT ограничена HS256, issuer и audience. Старые самодостаточные JWT больше не принимаются.

### 4. Высокий риск: приём файлов происходил до авторизации и оставлял временные файлы

`index.js`: `express-fileupload` был глобальным. Гость мог отправить multipart с самостоятельно выбранными одинаковыми cookie/header CSRF либо на путь вне `/api`; после ответов 401/404 оставался временный файл. Ограничение 100 MB применялось к каждому файлу, не к сумме запроса; ограничений количества частей не было.

**Исправлено:** parser применяется только на `/api/upload`, после сессии, роли и CSRF; один файл, одна строка type, две multipart-части, ограниченные размеры полей, таймаут и отдельный лимит запросов. Каталог создаётся отдельно на запрос и удаляется после завершения/разрыва соединения. Caddy ограничивает тело запроса 101 MB; изображения дополнительно ограничены 10 MB, видео — 100 MB. Сохраняются allowlist расширений, проверка MIME по реальным байтам и случайные имена. Прямой ответ медиа получает `nosniff` и CSP sandbox. Реальная загрузка PNG прошла, SVG и маскирующийся под JPEG текст отвергнуты.

### 5. Высокий риск: секреты попадали в backend Docker-образ

`.dockerignore` исключал только `node_modules` и lock-файл. `COPY . .` включал backend `.env` и рабочие логи. Доступ к registry/образу мог раскрыть окружение; запрет HTTP-доступа к `.env` этого не исправляет.

**Исправлено:** `.env`, `.env.*`, логи и IDE-файлы исключены из build context; lock-файлы включены, используется `npm ci --ignore-scripts`. Проверено отсутствие `/app/.env` в работающем образе. Старые образы/registry/cache и опубликованные секреты требуют отдельной очистки/ротации.

### 6. Средний риск: выключенный контент был доступен через публичный API

`pageController`, `roomController`, `dishController`, `wineController` возвращали объекты с `is_active=false`, включая прямое чтение по id. Скрытие карточки только в React не защищало содержимое API.

**Исправлено:** гости получают только активные страницы, номера, блюда и вина. Существующая административная сессия позволяет админке получать выключенные записи для редактирования. Для страниц и номеров подтверждено на настоящей БД: анонимный запрос по id даёт 404, администратор видит запись. Доступные изображения остаются публичными по URL: флаг выключения контента не является механизмом защиты приватных документов.

### 7. Средний риск: CSRF не был привязан к сессии, вход принимал HTML-форму

Изначально сравнивались только два значения, предоставленные клиентом, а `/login` полностью обходил CSRF. Cookie использовала SameSite=Lax; Secure зависел от определения proxy-протокола.

**Исправлено:** CSRF сравнивается с непредсказуемым значением конкретной серверной сессии; Origin и Sec-Fetch-Site проверяются до изменяющих операций, включая вход. Вход принимает JSON. Cookie — HttpOnly, SameSite=Strict, Secure по умолчанию в production; отключение Secure разрешено в конфигурации только для localhost. Публичная заявка остаётся без административной сессии, но принимает только JSON, имеет лимит 5/15 минут и собственную валидацию.

### 8. Средний риск: слабая политика создания администраторов

Через защищённую регистрацию можно было создать администратора с паролем из одного символа. Более строгая проверка в CLI не применялась к HTTP API.

**Исправлено:** минимум 12 символов, максимум 72 байта для bcrypt, валидация email; создание пользователя и корзины объединено транзакцией. Отсутствующий пользователь проходит dummy bcrypt-проверку, сообщения о неверном email/пароле одинаковы. CLI умеет спрашивать пароль скрыто, без аргумента командной строки. Пароли существующих аккаунтов автоматически не заменяются — их нужно проверить/сменить отдельно.

### 9. Средний риск: у админки не было действующей строгой CSP и изоляции от сторонних скриптов

У nginx была только CSP Report-Only, которая ничего не блокирует; политика не содержала адреса для сбора отчётов. Публичные TravelLine/Метрика подключались общим layout. SPA-переход сохранял уже загруженные скрипты на экране администрирования.

**Исправлено:** на `/admin`, `/login` и вложенных путях действует CSP с `script-src 'self'`, `frame-src 'none'`, `object-src 'none'`, `frame-ancestors 'none'`, ограничением форм и base URL. Смена публичной/приватной зоны загружает новый документ до отображения формы. TravelLine и Метрика не монтируются на приватных страницах, удалён глобальный скрипт карт из HTML. Отключена запись сессий Webvisor; аналитические просмотры не передают query/hash и приватные referer.

Проверка реального nginx выявила и исправила потерю строгой CSP при внутреннем SPA redirect: entrypoint теперь отдаётся в контексте защищённого location. Chrome подтвердил наличие CSP и отсутствие запросов сторонних JS на входе/в админке.

**Осталось:** полная enforce-CSP публичного сайта всё ещё требует проверки реальных TravelLine, карт и аналитики на боевом домене. Публичная Report-Only политика не считается защитой от XSS. Строгая админская CSP проверена отдельно.

### 10. Средний риск: неправильное число доверенных proxy и недостаточное ограничение ресурсов

Express доверял двум переходам, хотя `/api` направляется Caddy прямо в backend. Дополнительный hop можно было подставить при прямом обращении к Express. Это не было подтверждённым обходом через штатный Caddy: Caddy по умолчанию перезаписывает входящие forwarded-заголовки.

**Исправлено:** один hop, альтернативный API proxy в nginx отключён, удалена небезопасная/ненужная нормализация URL. Добавлен общий API rate limit, обновлён express-rate-limit с группировкой IPv6, сохранены отдельные лимиты входа/заявок и добавлен лимит загрузок. Реальный Caddy не позволил обойти login limit сменой X-Forwarded-For. Ограничены память/CPU/PID backend; процесс работает без root и Linux capabilities, с no-new-privileges. Инициализатор меняет владельца только upload-volume, чтобы старые root-owned файлы не ломали загрузку после перехода на UID 1000.

Ограничители используют память одного процесса: перезапуск обнуляет счётчики, а горизонтальное масштабирование потребует общего хранилища лимитов. Объёмные DDoS и распределённый перебор требуют защиты на edge и MFA.

### 11. Средний риск: локальная HTTP-конфигурация могла использоваться на сервере

Основной Caddyfile имел `auto_https off`, хотя Docker публиковал 443. Наличие отдельного server-файла само по себе не включало HTTPS в действующей Compose-конфигурации.

**Исправлено:** локальные порты по умолчанию привязаны к loopback. Отдельный production Compose override монтирует server Caddyfile, включает HTTPS и принудительные Secure-cookie. Проверка конфигурации отказывается стартовать с HTTP для публичного домена, выключенными Secure-cookie, короткими или шаблонными секретами. Добавлены HSTS, nosniff, X-Frame-Options, Referrer-Policy и Permissions-Policy. В workflow применяется production override и явный Caddy reload после выкладки.

Реальный сертификат, настройки CDN, отсутствие открытых портов backend/БД и TLS на боевом сервере ещё нужно проверить после выкладки.

### 12. Средний риск: доверие SSH host key при каждом деплое без проверки

Workflow получал known_hosts через `ssh-keyscan` прямо перед подключением. При атаке на сеть/DNS это могло закрепить ключ атакующего сервера.

**Исправлено:** требуется заранее проверенный `SSH_KNOWN_HOSTS`, StrictHostKeyChecking=yes, приватный ключ временный и с правами 0600; данные secrets не вставляются как shell-код. Права GitHub token минимальны, внешние actions закреплены SHA. Перед деплоем выполняются тесты, сборка и audit high/critical; деплой проверяет точный протестированный commit. Контейнеры больше не останавливаются командой down до успешной сборки.

Перед следующим GitHub-деплоем необходимо добавить секрет `SSH_KNOWN_HOSTS`, сверив ключ сервера по доверенному каналу. Получение ключа только тем же сетевым соединением не доказывает подлинность сервера.

### 13. Средний риск: небезопасные URL из CMS

Ссылки из произвольного JSON страниц и аналитики не проходили единую проверку схем; пути страниц могли быть внешними или неоднозначными. Код допускает только одно место с `dangerouslySetInnerHTML`: очищаемые сервером новости.

**Исправлено:** safeLinkUrl блокирует javascript/data-схемы, protocol-relative адреса, обратный слеш, управляющие символы и credentials в URL; используется в SmartLink и административных ссылках. Медиа не принимает исполняемые схемы. Пути CMS ограничены внутренним путём. Обновлены React Router, Tiptap и sanitize-html. Добавлены тесты опасных URL, сохранены тесты XSS-очистки новостей.

### 14. Недостатки обработки ошибок и служебных поверхностей

Сырой SQL exception мог попадать в логи вместе со значениями запроса. Swagger был публичным; это не обход авторизации само по себе, но лишняя служебная поверхность. Source maps создавались и выдавались production-сборкой. Разрозненные npm install и исключённые из Docker lock-файлы делали зависимости непредсказуемыми.

**Исправлено:** клиент видит общие сообщения, в неожиданный error-log пишется тип исключения; служебные API доступны только ADMIN, API выдаёт no-store. Production source maps выключены. Установка воспроизводима по lock-файлам, `.env` явно не экспортируется сборщиком: разрешены только два публичных REACT_APP значения.

### 15. Недостатки восстановления и свежей установки

При проверке пустой PostgreSQL bootstrap пытался создать индексы отсутствующих таблиц events. Это мешало запуску нового изолированного экземпляра и восстановлению на чистой БД.

**Исправлено:** отсутствующие event-таблицы создаются перед индексами без alter/force. Проверены штатный bootstrap и сохранение существующей схемы. Базовую схему на совершенно новой БД по-прежнему нужно создать миграциями; bootstrap не перезаписывает существующие данные.

## Зависимости: до и после

Числа npm audit обозначают уязвимые пакеты в дереве, а не независимые подтверждённые способы взлома сайта.

| Область | До | После |
| --- | --- | --- |
| Backend, все зависимости | 24: 1 critical, 16 high, 6 moderate, 1 low | **0** |
| Backend, production | 20: 1 critical, 12 high, 6 moderate, 1 low | **0** |
| Frontend, всё дерево | 106: 4 critical, 39 high, 42 moderate, 21 low | **5 low**, 0 moderate/high/critical |

Источники исходных и итоговых данных: файлы `before-*-dependencies.json` и `after-*-dependencies.json` рядом с отчётом. Проверка проведена через настоящий npm registry.

Удалены неиспользуемые multer, uuid и yamljs; заменён YAML parser, обновлены Express/Sequelize/проверка формата файлов/санитизатор и транзитивные пакеты. Неподдерживаемая цепочка react-scripts заменена на Vite/Vitest, удалены неиспользуемые react-spring/sort-by. Обновлены Axios, React Router, Swiper и Tiptap. Поддерживаемый runtime — Node >=22.12, Docker использует Node 22.

Оставшиеся пять low-записей фронтенда происходят из **одного deepmerge advisory** и зависимых пакетов Material Tailwind/Flowbite. Исправленной версии upstream нет. В проверенном коде Material Tailwind получает статическую тему; путь передачи недоверенного CMS-объекта в deepmerge не найден. Тем не менее advisory не объявляется исправленным: требуется исправление upstream либо замена этих UI-зависимостей. Откат deepmerge ради зелёного счётчика не оставлен, поскольку он мог бы убрать более ранние исправления.

Некоторые громкие предупреждения из исходного audit не означали достижимый эксплойт именно здесь:

- Advisory jws прямо исключает пользователей `jsonwebtoken`, использующих синхронный verify API; обход подписи по этому CVE не заявляется. [Разъяснение разработчика](https://github.com/auth0/node-jws/security/advisories/GHSA-869p-cjfg-cm3x).
- Critical proxy-addr требует определённых IPv4-mapped IPv6 subnet-настроек, которых в проекте не было. [Advisory разработчика](https://github.com/jshttp/proxy-addr/security/advisories/GHSA-jqcg-44mw-7w3h).
- SQLi Sequelize требует контроля JSON path/cast ключей where; доказанного пути от публичного запроса к такому sink не найдено. Пакет всё равно обновлён. [Advisory](https://github.com/sequelize/sequelize/security/advisories/GHSA-6457-6jrx-69cr).
- Swiper действительно попадал в уязвимый диапазон, но подтверждённой передачи произвольного объекта параметров от гостя не найдено; пакет обновлён. [Advisory](https://github.com/nolimits4web/swiper/security/advisories/GHSA-hmx5-qpq5-p643).
- Оставшийся deepmerge: [описание и отсутствие исправленной версии](https://github.com/advisories/GHSA-gcqx-w48m-w2h4).

## Что проверено без подтверждения эксплойта

Проверены SQL/JSONB-запросы, маршруты CRUD и роль ADMIN, прямые id/slug, черновики/даты публикации новостей, хранилища браузера, HTML и ссылки CMS, загрузки/пути/расширения, CORS/CSRF, JWT/cookie, SMTP-заявки, Метрика, Docker/Compose, Caddy/nginx и GitHub deploy.

Не найден достижимый из публичного запроса sink для выполнения shell-команд, произвольного server-side HTTP-запроса или чтения произвольного файла. Запросы к Метрике формируются сервером на фиксированном API base; изменение адреса требует изменения серверного окружения. SMTP использует TLS/STARTTLS, фиксированного получателя из административных настроек, валидацию email и запрет загрузки удалённых/локальных вложений. Тесты проверяют header injection и отсутствие раскрытия SMTP-ошибок. Отсутствие найденного пути не является формальным доказательством отсутствия уязвимости.

## Действия перед production

1. Сделать проверенную резервную копию БД и upload-volume с ограниченным доступом.
2. Сменить боевой JWT_SECRET и все опубликованные секреты. Старый JWT-ключ нельзя использовать снова даже после очистки Git. Меняя пароль PostgreSQL, сначала сменить пароль роли в самой БД, затем согласованно обновить `.env` и пересоздать backend/DB-контейнеры. Простая замена POSTGRES_PASSWORD в существующем volume пароль роли **не меняет**. Локально автоматически изменён только JWT-ключ; боевые значения не менялись.
3. Удалить архив с секретами из всех веток/тегов истории и проверить forks, артефакты сборок, registry и резервные копии. Переписывание общего Git требует координации и отдельного контролируемого force push; этот аудит его не выполнял.
4. Добавить проверенный SSH_KNOWN_HOSTS в GitHub secrets; убедиться, что deploy-user имеет нужные права, а environment `production` настроен согласно принятому процессу выкладки.
5. Использовать Docker Compose >=2.24.4 (production override применяет `!override` для портов). Проверить домен в `Caddyfile.server` и PUBLIC_SITE_URL. Применить production override:

   ```bash
   HTTP_PORT=80 docker compose -f docker-compose.yml -f docker-compose.production.yml up -d --build
   HTTP_PORT=80 docker compose -f docker-compose.yml -f docker-compose.production.yml exec -T caddy caddy reload --config /etc/caddy/Caddyfile
   ```

   На существующей БД bootstrap создаст admin_sessions без удаления контента. Все старые JWT перестанут работать: администраторам нужно войти заново. Для ручного управления миграцией предусмотрен `20261111-admin-sessions.js`.
6. Сменить старые/слабые пароли администраторов. Пароль можно вводить скрыто:

   ```bash
   docker compose exec backend node scripts/create-admin.js admin@example.com
   ```

7. Проверить HTTPS/redirect и Secure-cookie на реальном домене, ответы `/admin`, `/login`, `/api/user/auth`, отказ `.env/.git`, закрытые порты БД/backend, доступность TravelLine/карт и SMTP. Для Caddy за CDN заново проверить trusted proxies: текущая схема рассчитана на Caddy как внешний edge.

## Что ещё усиливать

- **MFA/passkeys либо доступ к административному API через VPN/identity proxy.** Встроенная MFA пока отсутствует. Сложный пароль, CSRF и строгая CSP не предотвращают все виды фишинга. Закрывать нужно административные API, а не только HTML `/admin`; публичные чтения и заявки должны остаться доступны посетителям.
- Разделить роль БД для приложения и роль миграций: текущий Compose по умолчанию использует postgres, а bootstrap требует DDL-прав. Для минимальных прав нужно вынести миграции в отдельный шаг; автоматическое лишение прав сломало бы текущий запуск.
- Настроить журналы действий администраторов, оповещения о подозрительных входах и инцидентах, общий limiter при масштабировании, резервные копии с проверкой восстановления.
- Устранить 132 ошибки общей TypeScript-проверки. Production bundle и security-тесты проходят, но проверка типов всего проекта остаётся незелёной и в CI не объявлена пройденной.
- Дождаться исправления deepmerge/заменить UI-зависимости; регулярно обновлять lock-файлы и сканировать базовые контейнерные образы. Аудит npm не сканирует все системные пакеты ОС.
- Проверить боевой сервер: SSH/firewall, права файлов и Docker socket, CI secrets, бэкапы, внешние сервисы, DNS/CDN/TLS, ранее выданные учётные данные и журналы. Эти настройки нельзя подтвердить по локальному репозиторию.
