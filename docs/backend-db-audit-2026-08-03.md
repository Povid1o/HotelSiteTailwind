# Аудит backend и PostgreSQL — 2026-08-03

## Проверенный контур

- PostgreSQL работает в Docker-сервисе `db`; наружу порт не опубликован. Это отдельная БД проекта, а не локальный сервер, к которому по умолчанию подключается PgAdmin.
- Контейнер БД healthy; backend и публичный API отвечают.
- Неавторизованные `POST /api/pages` и `POST /api/upload` возвращают `401`; публичное чтение `GET /api/pages` доступно сайту.
- Тест записи/чтения ранее выполнен внутри откатываемой транзакции: данные не сохранялись.

## Фактическое содержимое

На момент аудита в БД есть один пользователь, три страницы (`/`, `/Vinery`, `/Shop`), семь категорий событий и справочники вин. Номеров, вин, блюд, мероприятий и их изображений нет.

Это означает, что текущая публичная часть отображает fallback-состояния, а не реальные редакционные данные. Перед приёмкой нужно создать тестовый набор сущностей через админку и проверить сохранение после перезагрузки.

## Критичные проблемы

1. **Схема не управляется миграциями.** Backend вызывает `sequelize.sync()` при каждом запуске, но в БД нет таблицы `SequelizeMeta`. В репозитории существуют миграции, однако они не являются источником истины. Это создаёт риск незаметного schema drift и опасных обновлений при изменении моделей.
   Кроме того, индексы на внешних ключах, которые создаёт миграция, в фактической БД отсутствуют. При росте номеров, вин и событий это ухудшит выборки и каскадные операции.
2. **Секреты инфраструктуры находятся в Compose-конфигурации.** Их необходимо вынести в `.env`, добавить `.env.example`, сменить уже раскрытые значения и не коммитить реальный файл окружения.
3. **Две параллельные предметные модели.** Старый каталог (`products`, `types`, `clases`, `product_infos`, `baskets`) сосуществует с актуальными сущностями номеров, блюд, вин и страниц. Старый каталог пустой и не используется новым UI, но сохраняет лишние маршруты и риск регрессий.
4. **Дефект legacy FK.** `product_infos.product_id` объявлен `NOT NULL`, а внешний ключ использует `ON DELETE SET NULL`. Удаление связанного legacy-продукта будет завершаться ошибкой БД. Для текущего UI это не блокер, но это нужно удалить вместе с legacy-контуром либо исправить в миграции.
5. **Неполный контентный контракт для V4.** В БД отсутствуют страницы/секции для `/Hotel`, `/Contacts`, `/Privacy` и V4-hero/CTA-настроек. Их нужно добавить миграцией/seed-скриптом, а не неявным `sync` при запуске.

## Значимые, но некритичные проблемы

- `cors()` открыт для всех origin; для production должен быть allowlist доменов.
- Статика подключена дважды, а каждый запрос к медиафайлу пишется в stdout. Это создаёт лишнюю нагрузку и шум в логах.
- Проверка JWT дублируется в `authMiddleware` и `checkRoleMiddleware`.
- В error middleware есть опечатка в тексте ответа; API не возвращает унифицированный `code`/`requestId`.
- Стартовый seed содержит тестовые/устаревшие тексты и внешние изображения. Их нельзя считать production-контентом.

## Безопасная последовательность исправления

1. Сделать резервную копию тома PostgreSQL и проверить восстановление.
2. Вынести секреты в `.env`, создать `.env.example`, заменить реальные ключи и пароли.
3. Отключить `sequelize.sync()` в production; завести нормальную таблицу истории миграций и baseline-миграцию существующей схемы.
4. Добавить V4 content pages/sections и редакторы админки; проверить реальные записи через UI.
5. После подтверждения, что legacy-каталог не нужен, удалить его отдельной миграцией и только после резервной копии.
6. Ограничить CORS, убрать двойную раздачу статики/отладочное логирование и унифицировать auth/error middleware.
